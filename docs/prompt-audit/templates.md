# Prompt 模板：现状与改后（18/18）

> 配套：[prompt-audit.md](../prompt-audit.md)。
> **落地状态**：§1 生成计划、§4 `/goal` 计划指针、§7 候选生成已在 2026-10-29 第 2 阶段
> 写进 `lib/prompt.mjs`（过 `npm run preflight`）；其余条目仍是方案态，实现时以本文件为准。
> `现状` 取自改写前的 `lib/prompt.mjs` 在样例卡上的真实渲染；`改后` 是目标模板。
> 占位符：`<…>` 表示由卡片/上下文注入；空数据时整行不出现。

## 0. 约定

- 首行固定 `动作 · 对象`；首行后空一行；块标签单独一行；块内一行一个事实/动作。
- 单行视觉宽度 ≤72 列（CJK 记 2），超宽由 `renderPrompt` 折行。
- 不用 `#` / `**` / `>`；唯一例外是「输出」块里要求模型产出的 Markdown 小节。
- 新增块：`证据要求`、`非目标`、`失败处理`、`示例`；`场景` 补进规范。
- 动作 prompt 目标长度：`plan` ≤1500 字，`exec` ≤1500 字，`reflect` ≤800 字；JSON 生成 ≤1200 字。

````text
一句话：做完之后能稳定做到什么。

```bash
````

### 1.2 问题映射

| 现象 | 因子 | 后果 |
|---|---|---|
| 背景缺 `约束` / `场景` / `已有计划` / `引用` | 证据先行 | 计划不知道边界，容易越界或重做 |
| 「先读 README、脚本、配置、产物、最近提交」没有说读什么、提取什么、怎么引用 | 证据先行 | 模型靠自觉做大量 recon；计划里的断言没有来源 |
| 「每步一个可验证动作」太薄 | 决策完整 | 步骤缺文件、命令、预期结果、失败模式 |
| `验收` 只是复述验收项 | 验收可追溯 | 步骤和验收各说各的，无法核对 |
| 「不要开始改代码」与 DSH 系统提示重复 | — | 浪费 token，且可能与系统提示冲突 |
| `验收` 块和目标验收重复 | — | 同一事实出现两次，气泡变长 |

```text

背景
- 项目：<项目名>（<workspace>）
- 闭环：<闭环标题>
  - 意图：<闭环意图>
  - 约束：<闭环约束>
- 目标：<目标标题>
  - 验收：<目标验收>
- 构思：<构思标题>
  - 方向：<构思方向>
- 场景：<落地场景流程>
- 已有计划：<计划目标>（<步骤数> 步）
- 引用：<引用节点与状态>

1. 先读：README、package.json/脚本、相关源码与测试、最近提交、产物。
2. 给出 3–5 条可核对事实，每条带 path:line 或命令输出。
3. 先复现或确认当前行为；无法复现就写清卡在哪。
4. 列出未决问题；查不到就写假设，不要猜 API/字段/命令。

任务
产出可执行计划，做完能稳定达到「<目标标题>」。
成功标准：
- 每个改动点有文件路径与具体动作。
- 每一步有可执行验证命令与预期结果。
- 覆盖边界/失败模式；写明非目标。
- 每个验收项都能追溯到某一步。

非目标
- 不重构无关代码；不升级依赖；不改 <明确排除的文件/行为>。

验收
- <验收项 1>
- <验收项 2>

输出
用 Markdown，三节顺序固定：
## 目标
一句话：做完之后能稳定做到什么。
## 验证命令
可直接执行的 bash 命令，一行一条；每条写清预期结果。
## 步骤
1. 改哪些文件 / 做什么 / 验证命令 / 预期结果 / 对应验收项。
2. …

提交方式
- 写完用 exit_plan_mode 提交，plan 传完整 markdown。
- 不要直接开始执行。
```

### 1.4 差异与影响

- 新增 `约束` / `场景` / `已有计划` / `引用`：补上下文，改 `background` 拼装。
- 新增 `证据要求`：把「读文件」变成可核对的事实与引用。
- `要做什么` → `任务`，加成功标准；新增 `非目标`。
- `输出` 的 `## 步骤` 加「文件 / 命令 / 预期 / 验收项」。
- 删除与系统提示重复的「不要开始改代码」解释；保留 `exit_plan_mode` 约束。
- 预计长度：1200–1500 字；`plan` 上限不变。
- 契约不变：三节标题、`exit_plan_mode`、`/plan` 发送方式。
- lint：`证据要求` / `非目标` 需进 `BLOCK_LABELS`；否则 `empty-block` 不检查（不会误报，但规范不完整）。

## 7. 候选生成（`composeCandidatePrompt`，`lib/prompt.mjs:750`）

### 7.1 现状（静态部分）

```text
要做什么
1. 先读项目里的文件（README、脚本、配置、产物）再作答。
2. 给出 3 条互不重复的候选<子节点类型>，每条都要能独立验证。
3. 这 3 条是同一目标的互斥路线，最终只会采纳 1 条。   ← 仅构思候选

约束
- 标题 8–16 字，说清「做到什么」（构思写「走哪条路」）。
- 每条先写一句优势（strength）：为什么比其它候选更强，要能横向比较，不写空话。 ← 仅构思候选
- 每条给一句验收（可判定的检查、命令或判据）。

输出
严格只输出 JSON 数组：[{"title":"…","strength":"…","acceptance":"…"}]
不要输出其它文字。
```

### 7.2 问题

- 没有 `constraints` / `scenario`，候选可能越过闭环边界。
- 对非构思候选，`strength` 分支容易混；输出契约在两个分支之间切换，示例缺失。
- `第 2 条` 的「3 条」写死，`count` 参数变化时文案不一致（当前函数支持 `count`）。

### 7.3 改后

```text
任务
给出 <N> 条互不重复的候选<子节点类型>，每条都能独立验证。
成功标准：
- 每条满足闭环约束与场景流程。
- 候选之间无重复、无包含，可独立采纳。
- 每条验收是命令/断言/可观察结果。

证据要求
- 先读 README、脚本、配置、产物；不确定就查，不编。

约束
- 标题 8–16 字，说清「做到什么」（构思写「走哪条路」）。
- 每条给一句验收（可判定的检查、命令或判据）。
- 构思候选额外给一句优势（strength）：显式对比另两条候选，写清强在哪（少几次写 / 少几个状态 / 少一轮返工），不要用「最小 / 最强」这类没有对比对象的词。

输出
严格只输出 JSON 数组：[{"title":"…","acceptance":"…"}]
构思候选：[{"title":"…","strength":"…","acceptance":"…"}]
只含这 <N> 条，不要输出其它文字。

示例
[{"title":"素材入库可追溯","acceptance":"`GET /api/lessons` 返回该素材，`cueCount>0`"}]
```

### 7.4 影响

- 补 constraints/scenario 注入；修 `count` 文案；加示例。
- 契约不变（两类数组），但需要测试覆盖两个分支。

### 7.5 里程碑 → 目标：阻碍驱动（2026-10-30 落地）

用户反馈「自动生成的目标脱离里程碑、比较抽象」。归因：7.3 的「差异轴」是**覆盖度**目标，
里程碑分支真正要的是**清除度**目标——每条候选消除一条现在就挡住里程碑的阻碍。
所以里程碑分支不再用 7.3 的任务块，改为：

```text
背景
- 阻碍项（每条候选只认领其中一条）：
  1) <阻碍：缺什么 → 挡在愿景哪一步 → 涉及模块>
  2) …

任务
给出 <min(请求条数, 阻碍条数)> 条候选目标，每条只解决一条阻碍项，最终只采纳 1 条。
成功标准：
- 每条候选认领一条不同的阻碍项；阻碍项比条数多时，取最挡核心指标的几条。
- 先复现阻碍现状（读代码 / 跑命令 / 看产物），证据写进 evidence；复现不出来就换一条阻碍。
- 验收是「阻碍消除后能观察到的判据」（命令 / 断言 / 可见结果），不是功能清单、不是口号。
- 候选之间无重复、无包含，可独立采纳。

约束
- 标题 8–16 字名词短语，说清「消除哪条阻碍」，不写口号、不写手段。
- blocker 照抄阻碍项原文的短名（≤80 字），不改写、不概括。
- evidence ≤200 字：指到文件 / 命令 / 输出，不写「已确认」「目前缺失」这类空话。
- 每条给一句验收（可判定的检查、命令或判据）。

输出
严格只输出 JSON 数组，字段名固定为 blocker / evidence / title / acceptance：
[{"blocker":"…","evidence":"…","title":"…","acceptance":"…"}]
只含这 <N> 条，不要输出其它文字。
```

要点：

- **条数受阻碍约束**：`want = min(count, 阻碍条数)`，不允许为凑数编没有阻碍承接的候选。
- **阻碍项为空直接拒绝**（`BLOCKERS_REQUIRED`）：没有阻碍就没有「阻塞点」，退回愿景缺口
  正是抽象目标的来源。
- **目标 → 构思分支不变**：那里要的是同一目标的互斥路线，差异轴与 `strength` 仍然有效。
- 输出契约多两个字段（`blocker` / `evidence`），落库与候选池行都要保留，否则面板又只剩标题。

### 8.4 列表字段改 JSON 数组（2026-10-30 落地）

用户反馈「阻碍项生成时多条条目融合在一起」。根因不在「模型乱写」——模型按「一条一行」写了 `○` 前缀 +
单换行，是**条目编辑器不认 `○`**：`parseItems()` 认不出符号就退回 plain 模式（只按空行切），5 条变 1 块。
两处一起改：

- **契约**：列表字段（`blockers` / `metrics` / `acceptance` / `constraints` / `scenario`）的 JSON 值是
  **字符串数组**，一条一个元素；元素内不换行、行首不加符号。字符串字段（`vision` / `title` / `verify`）保持字符串。
- **归一**：`lib/core.mjs` 的 `normalizeListValue()` 把数组 / 旧字符串统一成「一条一行、每行 `N)`」，
  去掉 `1) A. 一、 ● ○ ①` 这类前缀再统一编号；小数（`1.5 倍`）与以数字开头的正文（`89 份…`）不误剥。
- **解析**：`ITEM_RE` 扩到 `[-•*○◯·∙▪◦]` 与 `[①-⑳]`，编辑器打开历史融合块即拆成多条，保存时归一。
- **不改存量**：旧的融合字段不动，下次打开编辑器按新规则显示。

验证：`scripts/list-fields-mock.mjs` 25 条断言；另外用假 ctx 跑 `POST /api/fill`
（模型返回数组）确认落盘是 `1)…\n2)…`。
